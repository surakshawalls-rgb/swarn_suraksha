# SwarnaSuraksha

Angular 21 + Ionic foundation for a multi-business jewellery management system. This phase adds a shared Supabase client, Google OAuth sign-in, session restoration, guarded dashboard routing, a real membership/profile connectivity check, business selection and initial workspace creation.

## Local development

1. Install Node.js 20.19+, 22.12+, or 24 and npm. Run `npm install`, then `npm start` (Angular serves `http://localhost:4200`).
2. The development environment uses the configured SwarnaSuraksha Supabase project and its browser-safe anon/publishable key. The key is public by design; never place a service-role key or Google client secret in Angular.
3. In Supabase **Authentication → Providers → Google**, enable Google and store the Google client ID and client secret there. In Google Cloud, use a Web application client, add `http://localhost:4200` as an authorized JavaScript origin, and add `https://woikgebywlobpjlihzej.supabase.co/auth/v1/callback` as the authorized redirect URI.
4. In Supabase **Authentication → URL Configuration**, set the development Site URL to `http://localhost:4200` and add `http://localhost:4200/**` to Redirect URLs. The app returns to `http://localhost:4200/auth/callback`.
5. Run `supabase/diagnostics/user_profiles_inspection.sql` in the Supabase SQL editor and review the output. If the live schema confirms one UUID profile per user and the existing trigger/function design does not own profile creation, apply `supabase/migrations/003_user_profiles_owner_access.sql`. It preserves rows, requires a unique `user_id` index, restricts reads/inserts/updates to `auth.uid()`, and grants only those operations to `authenticated`. Do not apply `002_authenticated_access_grants.sql` blindly; inspect all referenced tables and existing policies first. I could not access an authenticated Supabase dashboard/database session from this environment, so neither migration has been applied to the hosted project.

The repository's `001_swarnasuraksha_foundation.sql` is the original foundation migration. Do **not** run it against the current project blindly: read-only API probes find `user_profiles`, `business_profiles`, `business_members`, `business_settings`, `customers`, and `audit_logs`, while `metal_rate_snapshots` is not present in the exposed PostgREST schema (or its schema cache). The history/schema still needs authenticated inspection. Compare the migration with the live project before applying it anywhere.

## Production

`src/environments/environment.production.ts` uses the same Supabase project URL and public key because no separate production Supabase project was supplied. The production redirect is derived from the deployed page origin and ends at `/auth/callback`. Add the real deployed origin and callback path to Supabase's Redirect URLs when the domain is known; no production domain or DNS was invented. Google Cloud also needs the deployed web origin. The Supabase callback URI remains the provider redirect URI.

## Current foundation scope

- Google OAuth with a fixed same-origin callback, loading/error states, cancellation reporting, automatic session detection, refresh persistence, auth-state subscription, sign-out, and an authentication route guard.
- A responsive workspace shell and tenant-scoped overview are in place. The overview shows active customer/supplier counts, latest manual rate, sales billed, and outstanding customer/supplier balances. Financial summaries call `ss_dashboard_summary`, delivered as additive migration `009_dashboard_summary.sql`; review `supabase/diagnostics/dashboard_summary_inspection.sql` and verify/apply it against the hosted schema. If the RPC is not installed, the UI shows an explicit unavailable state. Angular 21 uses zoneless change detection by default; asynchronous auth/workspace state explicitly marks views for refresh.
- Workspace onboarding calls the existing `create_business` RPC. The authenticated check upserts the user's own profile once per app session and reads membership rows plus RLS-visible businesses; a membership row without a readable business row does not grant workspace selection.
- The `/auth/callback` route verifies the session and upserts `user_profiles.user_id` from the authenticated user UUID. A profile failure leaves the session intact and presents a retry option.
- Customers now has tenant-scoped search, paging, create/edit, duplicate warnings, and archive/restore. It relies on the hosted `customers` table, grants, and RLS, which still require live-schema verification before production use.
- Customer statements now use `ss_customer_ledger_page` to show chronological invoice debits, receipt credits, return credits, and refund debits, with date filters, exact opening/closing balances, running balances, pagination, print, and formula-safe current-page CSV. Positive balance means due; negative balance is a customer credit. Walk-in sales without a customer link and pledge history are excluded. Review `supabase/diagnostics/customer_transaction_ledger_inspection.sql` and apply additive migrations `017_customer_statement_read_model.sql` and `018_customer_transaction_ledger.sql` only after hosted schema/helper verification.
- Suppliers now has tenant-scoped search, paging, create/edit, duplicate warnings, archive/restore, and purchase statements with formula-safe CSV export. Apply `supabase/migrations/004_suppliers.sql` only after confirming its preflight passes against the hosted membership helpers; the migration aborts if those helpers are absent or unusable.
- The rates screen records append-only manual gold/silver snapshots with separate reference and shop prices, reason, unit/purity, and server timestamp. It never labels manual entries as live market data. Apply `supabase/migrations/005_manual_rate_snapshots.sql` only after checking hosted membership helper compatibility; it aborts if its prerequisites are absent or unusable.
- Purchases now has a server-atomic posting workflow: supplier, weighted item lines, partial/split payments, owned inventory movements, linked cashbook outflows, idempotent retry, and safe audit metadata. Apply `supabase/migrations/006_purchases_inventory.sql` only after running `supabase/diagnostics/purchase_ledger_inspection.sql` and confirming the hosted schema and membership helpers; it aborts if prerequisites are missing. The migration has not been applied or exercised against the hosted database.
- Owned inventory is available at `/dashboard/inventory`. It derives current net weight by metal/purity from separate purchase, sale, and full-line return movement ledgers; includes tenant-checked, paginated movement history and formula-safe current-page CSV. Customer pledged items are excluded. Review `supabase/diagnostics/owned_inventory_inspection.sql`, then apply additive migration `015_owned_inventory_read_models.sql` only after its hosted schema and helper preflight matches. This is a weight ledger, not item/location tracking or valuation, and no stock adjustment workflow is enabled.
- Sales now has server-atomic posting from selected manual shop-rate snapshots with optional customer, partial/split payments, stock availability checks, owned-stock reduction, cashbook inflows, audit metadata, and safe idempotent retry. Apply `supabase/migrations/007_sales_billing.sql` only after `supabase/diagnostics/sales_ledger_inspection.sql` confirms the hosted base tables, constraints, helper functions, grants, and RLS. This migration is additive and has not been applied or exercised against hosted data.
- Cashbook uses the tenant-checked `ss_cashbook_page` RPC to merge purchase outflows, sale collections, return refunds, and owner/admin-only operating-expense outflows before pagination, with page totals and formula-safe CSV export. Review `supabase/diagnostics/cashbook_paging_inspection.sql` and `supabase/diagnostics/operating_expenses_inspection.sql` before applying additive migrations `013_cashbook_paging.sql` and `014_operating_expenses.sql`. It does not present an absolute balance because opening balances and cash accounts are not configured.
- Invoice settlement/collection controls are available to owners and admins for outstanding purchases and sales. Migration `008_account_payments.sql` performs each later payment atomically, with idempotent retries, bill balance updates, cashbook entries, and audit events. Review `supabase/diagnostics/account_payments_inspection.sql` against hosted metadata before applying it; it has not been applied or exercised on the hosted database.
- Reports are available to owners/admins at `/dashboard/reports`. The daily view filters up to 366 days and aggregates posted sales, returns, purchases, paid operating expenses, payment movements, and owned-stock weight changes. CSV exports require a server-recorded export audit event. Review `supabase/diagnostics/business_reports_inspection.sql` and apply migration `010_business_reports.sql` first; migration `014_operating_expenses.sql` adds the expense-aware `ss_business_report_v3`. Both require hosted schema/helper verification and have not been applied to the hosted database. The report is not a cash balance, stock valuation, complete accounting statement, or girvi report.
- Owners/admins can record paid operating costs at `/dashboard/expenses`. Expense posting and its cashbook/audit records are atomic and idempotent; staff and anonymous users cannot post or read expense details. Tax is not calculated, unpaid bills are outside this screen, and corrections require a separately designed adjustment workflow. Review `supabase/diagnostics/operating_expenses_inspection.sql`, then apply additive migration `014_operating_expenses.sql` only after its prerequisites match the hosted database.
- Owners/admins can inspect the unified audit feed at `/dashboard/audit`. A membership-checked server RPC merges the existing purchase, sale, payment, return, expense, receipt-print request, and report-export events with date/type filters, pagination, and current-page CSV. It does not expose audit tables directly to the client. Review `supabase/diagnostics/admin_audit_feed_inspection.sql`; apply `supabase/migrations/016_admin_audit_feed.sql` only after hosted preflight. User/role management, notification delivery events, and audited export of the audit log itself remain future work.
- The app shell displays browser online/offline state. Purchase, sale, and later payment posting are disabled while offline; no offline financial ledger is implemented. A request interrupted after submission retains an idempotent retry path.
- Sales receipts now offer A4 and 80 mm thermal print layouts using saved invoice, line, rate, payment, and balance data. The print action is audited server-side before opening the device print dialog; the app does not claim physical print success. This receipt is not a GST tax invoice while tax is unconfigured. The audit RPC/table are included in migration `010_business_reports.sql` and require the same hosted diagnostics and application.
- Purchases now offer an A4 or thermal supplier goods-received voucher using the saved purchase, line, supplier, and payment records. Print requests are audited server-side by additive migration `011_purchase_receipt_audit.sql`; inspect the purchase ledger diagnostic before applying it. A printed voucher does not confirm supplier payment or tax treatment.
- Business decisions currently supplied: GST/tax remains configurable but disabled until configured; girvi pledge posting remains disabled until interest, partial-period, repayment allocation, and release rules are provided; rates use manual snapshots only.
- Sales returns reverse complete invoice lines at the saved no-tax amount, reduce unpaid balance first, restore owned stock, and record only eligible refunds. Return vouchers have A4/thermal previews and audited print requests. Migration `012_sales_returns.sql` is additive and pending hosted diagnostics/application. Partial quantity returns, enabled tax configuration, girvi, opening-balance/account reconciliation, role settings, notifications, and Android integration remain. Girvi posting intentionally stays disabled pending business rules. The full plan and unresolved business decisions are in `IMPLEMENTATION_PLAN.md`.
